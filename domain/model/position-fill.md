# PositionFill

## Overview

Records a single executed fill (BUY or SELL) for a stock position within an account, owned by the Portfolio domain. A `PositionFill` row is created every time the Portfolio domain consumes an `OrderFilledEvent` from the Stock Trading domain. It forms the time-series dataset used to render the Advanced Insights price history chart.

`PositionFill` is a read model owned entirely by the Portfolio domain. It is populated from `OrderFilledEvent` payloads and is never written to by any other mechanism. It does not replace or duplicate `Position` — `Position` holds the current aggregated state; `PositionFill` holds the ordered sequence of individual fills that built that state.

## Properties

| Field | Type | Required | Description |
|-------|------|:--------:|-------------|
| id | uuid | yes | Unique fill record identifier, generated by the Portfolio domain on event consumption. |
| userId | uuid | yes | Reference to the owning user. Denormalised from the event payload. |
| accountId | uuid | yes | Reference to the account that funded the order. Foreign key stored as UUID only — no JPA join to the Ledger domain. |
| ticker | string | yes | 4-letter stock ticker symbol (e.g. `AAPL`). |
| assetType | enum | yes | `STOCK` — only value in this iteration. |
| side | enum | yes | `BUY` \| `SELL`. Copied from the `OrderFilledEvent` payload. |
| executionPrice | decimal | yes | Price per share at which the order was filled. Copied from the `OrderFilledEvent` payload. |
| quantity | decimal | yes | Number of shares filled. Copied from the `OrderFilledEvent` payload. |
| filledAt | datetime | yes | Timestamp of the fill. Set from the `timestamp` field of the `OrderFilledEvent` payload. |
| idempotencyKey | uuid | yes | The `idempotencyKey` from the source `OrderFilledEvent`. Used to enforce exactly-once processing. Unique constraint. |

## Behaviors

- **RecordFill**: On receipt of an `OrderFilledEvent`, the Portfolio domain listener checks the `idempotencyKey` against the `portfolio_processed_events` log. If absent, a new `PositionFill` row is inserted and the key is recorded — both in the same transaction. If the key is already present, the event is silently discarded.

## Events

_None emitted. `PositionFill` is a pure read model — it is written once and never updated._

## Relationships

- **Position** (`many-to-one` by convention): Many fills contribute to one `Position` (same `userId` + `accountId` + `ticker`). There is no JPA foreign key — the relationship is logical, navigated by querying fills with matching `userId`, `accountId`, and `ticker`.
- **User** (`many-to-one`): Reference by `userId` (UUID) only.
- **Account** (`many-to-one`): Reference by `accountId` (UUID) only — no JPA join to the Ledger domain.

## Business Rules

- A `PositionFill` row is created for every `OrderFilledEvent`, regardless of `side`. Both BUY and SELL fills are recorded.
- `idempotencyKey` must be unique across all `PositionFill` rows. A duplicate key means the event has already been processed; the record is silently discarded. Idempotency is shared with the `portfolio_processed_events` log already used by `Position` — a single log entry covers both the `Position` update and the `PositionFill` insert within the same transaction.
- `PositionFill` rows are immutable after creation. No updates are permitted.
- `assetType` is currently always `STOCK`. Adding a new value requires a corresponding decision log entry.
- The Portfolio domain must not import from `stocktrading.model`, `stocktrading.repository`, or `stocktrading.service` to populate this entity. All data comes exclusively from the `OrderFilledEvent` payload.
- There is no retention or deletion policy in this iteration. All fills are retained indefinitely.
