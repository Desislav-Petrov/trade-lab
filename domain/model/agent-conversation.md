# AgentConversation

## Overview

Represents a single multi-turn conversation between an authenticated user and the Trade Lab AI Assistant, held exclusively in the backend's in-memory ADK session store within the `agent` domain. A conversation is created lazily on the first `POST /api/v1/agent/query` call carrying a previously unseen `conversationId` and accumulates every subsequent user turn and agent turn for that `conversationId`. It is never persisted to the database — it lives only in the Google ADK for Java in-memory session service and is lost when the backend restarts.

The `conversationId` is generated by the frontend (one per open conversation) and sent on every turn. The backend keys the ADK session by this `conversationId` so the agent retains context across turns. The frontend keeps its own copy of the transcript purely for display; that copy lives in frontend session state and is lost on page reload.

## Properties

| Field | Type | Required | Description |
|-------|------|:--------:|-------------|
| conversationId | uuid | yes | Frontend-generated identifier for the conversation. Acts as the ADK session key. Sent on every `POST /api/v1/agent/query` request in the conversation. |
| userId | uuid | yes | The authenticated user who owns the conversation. Resolved server-side from the JWT — never taken from the request body. Also the identity supplied to the Portfolio Analyst's holdings tool. |
| accountId | uuid | yes | The account selected in the frontend when the conversation began. Carried on every request and consumed by the Portfolio Analyst's holdings tool to scope portfolio retrieval to this single account. |
| turns | list | yes | Ordered list of turns in the conversation. Each turn is either a user message or an agent reply. Held by the ADK session. |
| createdAt | datetime | yes | Timestamp of the first query that created the conversation. |
| updatedAt | datetime | yes | Timestamp of the most recent turn appended to the conversation. |

## Behaviors

- **Create**: On the first `POST /api/v1/agent/query` with an unseen `conversationId`, the `AgentService` opens (or lets ADK open) an in-memory session keyed by that `conversationId`, records `userId` and `accountId`, and appends the first user turn.
- **Append turn**: On each subsequent query with an existing `conversationId`, the user message is appended and the streamed agent reply is appended as the agent produces it. The ADK session carries prior turns into the Main Agent invocation so context is preserved.
- **Scope holdings tool**: When the Portfolio Analyst calls its holdings tool, the conversation's `accountId` and the JWT-resolved `userId` scope the retrieval to that user's holdings for that single account. See `domain/flows/agent-assistant-chat.md` — Flow E.
- **Stream reply**: The agent reply is streamed back to the caller token-by-token via Server-Sent Events (ADK `StreamingMode.SSE`) as it is generated, then appended to `turns` on completion.
- **Expire on restart**: The conversation exists only in the ADK in-memory session service. A backend restart discards all conversations. A frontend that later sends an old `conversationId` to a restarted backend is treated as a new conversation (empty context).

## Events

_No domain events are emitted by this concept. It is an in-memory session structure internal to the `agent` domain._

## Relationships

- **User** (`reference`): Each conversation belongs to exactly one user via `userId`. Reference by ID only — no foreign key, no shared entity across domains.
- **Account** (`reference`): Each conversation is associated with one `accountId` selected in the frontend at the time the conversation began. Reference by ID only. The `agent` domain stores the UUID, never the `Account` entity.
- **Position** (`reference`): Read indirectly via the Portfolio `api/` interface when the Portfolio Analyst's holdings tool runs. The `agent` domain consumes only the tool result — it never holds `Position` entities or reads the Portfolio database directly.

## Business Rules

- `AgentConversation` is in-memory only. It is never written to the database.
- Conversations are keyed by `conversationId`. There is at most one active conversation per `conversationId`.
- `conversationId` is generated by the frontend, not the backend. The backend trusts it as the session key but always resolves `userId` independently from the JWT.
- A conversation may only be created for an authenticated user whose request carries a valid JWT. Unauthenticated requests are rejected with HTTP 401 before any conversation is created.
- `userId` is always resolved from the JWT and never from the request body.
- `accountId` is recorded on the conversation and consumed by the Portfolio Analyst's holdings tool to scope portfolio retrieval to a single account. Cross-account reasoning within a conversation is not supported.
- All conversation state is lost on backend restart. There is no durability guarantee and no cross-instance sharing.
