# AgentConversation

## Overview

Represents a single multi-turn conversation between an authenticated user and the Trade Lab AI Assistant, held in the backend's ADK session store within the `agent` domain. A conversation is created lazily on the first `POST /api/v1/agent/query` call carrying a previously unseen `conversationId` and accumulates every subsequent user turn and agent turn for that `conversationId`.

The verbatim turn-by-turn session is **ephemeral** — it is not durably stored and is discarded when the backend restarts. Continuity across restarts, frontend reloads, and a user starting a new conversation is instead preserved by a durable, user-scoped `ConversationSummary` (ADK state key `last_conversation`), which the agent presents as an opening summary when the user returns. See `domain/model/conversation-summary.md` and `decisions/2026-10-10-agent-conversation-summary-continuity.md`.

The `conversationId` is generated by the frontend (one per active conversation) and sent on every turn. The backend keys the ADK session by this `conversationId` so the agent retains verbatim context across turns while the backend keeps running. The frontend keeps its own copy of the transcript purely for display; that copy lives in frontend session state and is lost on page reload. After a reload or restart the agent re-establishes continuity from the user-scoped `ConversationSummary` rather than the lost verbatim history. There is at most one active conversation per user — the platform does not track or let the user browse multiple past conversations.

## Properties

| Field | Type | Required | Description |
|-------|------|:--------:|-------------|
| conversationId | uuid | yes | Frontend-generated identifier for the active conversation. Acts as the ADK session key. Sent on every `POST /api/v1/agent/query` request in the conversation. A new value is generated when the user starts a new conversation. |
| userId | uuid | yes | The authenticated user who owns the conversation. Resolved server-side from the JWT — never taken from the request body. Also the identity supplied to the Portfolio Analyst's holdings tool and the key for the user-scoped `ConversationSummary`. |
| accountId | uuid | yes | The account selected in the frontend when the conversation began. Carried on every request and consumed by the Portfolio Analyst's holdings tool to scope portfolio retrieval to this single account. |
| turns | list | yes | Ordered list of turns in the conversation. Each turn is either a user message or an agent reply. Held by the ephemeral ADK session; not durably persisted. |
| createdAt | datetime | yes | Timestamp of the first query that created the conversation. |
| updatedAt | datetime | yes | Timestamp of the most recent turn appended to the conversation. |

## Behaviors

- **Create**: On the first `POST /api/v1/agent/query` with an unseen `conversationId`, the `AgentService` opens (or lets ADK open) a session keyed by that `conversationId`, records `userId` and `accountId`, and appends the first user turn.
- **Append turn**: On each subsequent query with an existing `conversationId`, the user message is appended and the streamed agent reply is appended as the agent produces it. The ADK session carries prior turns into the Main Agent invocation so context is preserved while the backend keeps running.
- **Scope holdings tool**: When the Portfolio Analyst calls its holdings tool, the conversation's `accountId` and the JWT-resolved `userId` scope the retrieval to that user's holdings for that single account. See `domain/flows/agent-assistant-chat.md` — Flow E.
- **Stream reply**: The agent reply is streamed back to the caller token-by-token via Server-Sent Events (ADK `StreamingMode.SSE`) as it is generated, then appended to `turns` on completion.
- **Update summary**: After each completed turn, the backend regenerates the user-scoped `ConversationSummary` (`last_conversation`) from the current conversation so continuity survives restart, reload, and a new-conversation reset. See `domain/model/conversation-summary.md`.
- **Start new conversation**: When the user clicks "New conversation", the frontend generates a fresh `conversationId`, abandoning the previous session. The previous conversation becomes unreachable. The user-scoped `ConversationSummary` carries forward unchanged until the new conversation produces its first summary update. See `domain/flows/agent-assistant-chat.md` — Flow F.
- **Discard verbatim on restart**: The verbatim ADK session is ephemeral and is discarded on backend restart. A frontend that later sends an old `conversationId` to a restarted backend is treated as a new session with empty verbatim context; continuity is recovered from the user-scoped `ConversationSummary`, which the agent presents as an opening summary (Flow G).

## Events

_No domain events are emitted by this concept. It is a session structure internal to the `agent` domain._

## Relationships

- **User** (`reference`): Each conversation belongs to exactly one user via `userId`. Reference by ID only — no foreign key, no shared entity across domains.
- **Account** (`reference`): Each conversation is associated with one `accountId` selected in the frontend at the time the conversation began. Reference by ID only. The `agent` domain stores the UUID, never the `Account` entity.
- **ConversationSummary** (`reference`, one per user): Each conversation feeds the durable, user-scoped `ConversationSummary` keyed by `userId`. The summary is derived from the conversation's turns and persists independently of the ephemeral session. See `domain/model/conversation-summary.md`.
- **Position** (`reference`): Read indirectly via the Portfolio `api/` interface when the Portfolio Analyst's holdings tool runs. The `agent` domain consumes only the tool result — it never holds `Position` entities or reads the Portfolio database directly.

## Business Rules

- `AgentConversation` verbatim turn history is ephemeral and is not durably persisted. Only the derived user-scoped `ConversationSummary` is durable.
- Conversations are keyed by `conversationId`. There is at most one active conversation per user at a time; the platform does not track multiple conversations.
- `conversationId` is generated by the frontend, not the backend. The backend trusts it as the session key but always resolves `userId` independently from the JWT.
- A conversation may only be created for an authenticated user whose request carries a valid JWT. Unauthenticated requests are rejected with HTTP 401 before any conversation is created.
- `userId` is always resolved from the JWT and never from the request body.
- `accountId` is recorded on the conversation and consumed by the Portfolio Analyst's holdings tool to scope portfolio retrieval to a single account. Cross-account reasoning within a conversation is not supported.
- The verbatim session is lost on backend restart and on frontend reload. Continuity is preserved via the user-scoped `ConversationSummary`, not the verbatim history.
